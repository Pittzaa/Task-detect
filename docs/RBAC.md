# Roles, scopes and permissions

## Concepts
* **Permission** — one capability from a fixed catalog (`src/authz/permissions.ts`). Unknown strings in the database grant nothing.
* **Role** — a named set of permissions. **System roles** (`orgadmin`, `manager`, `member`, `viewer`) are global and synced from code by `syncSystemRoles`; **custom roles** belong to one organization and are created by administrators (`org.manage_roles`).
* **Role assignment** — `(membership, role, scope)`. One person can hold several, e.g. *manager* in Team A and *viewer* in Project B.
* **Scope** — `organization | department | team | project`. Exactly one scope column is set, as a composite foreign key `(org_id, id)`, so a scope can never point into another organization.
* **`superadmin`** is **not** an organization role: it is a platform flag (`users.is_platform_admin`) that grants **nothing** inside any organization. No in-application powers are implemented for it (a deliberate choice: no operator access to tenant content without a separate, audited process).

## Evaluation rules (`src/authz/evaluate.ts`, pure and unit-tested)
1. The membership must be **approved**; `pending`, `suspended` and `revoked` reach nothing (the API answers 404).
2. The resource’s `orgId` must equal the principal’s.
3. A permission is granted if **any** assignment carries it **and** its scope covers the resource.
4. Coverage: `organization` covers everything in the org; `department` covers that department, its teams and the projects its teams participate in; `team` covers that team and the projects it participates in (and their tasks); `project` covers exactly that project and its tasks.
5. **Union only, deny by default** — there are no explicit denies. No matching assignment → denied.
6. The scope chain of a resource (its department/team/project ids) is always loaded from the database, never taken from the request.

Safeguards in the services: no privilege escalation (`assertCanGrantRole`: you can only grant roles whose permissions you hold at that scope), last-administrator protection (advisory lock), no self-suspension, custom roles may only contain catalog permissions, and **unreadable resources return 404 rather than 403** so existence is not disclosed.
What the UI shows is a *hint* (`/api/orgs/:id/context` returns capability flags; `createTask`/`manageSeries` mean “somewhere in the org”); the server decides every action.
