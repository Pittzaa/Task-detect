# Security

This document states what the application does to protect tenants, **how each claim was checked**, and what is *not* covered.
It does not claim the application is “secure”: it reports the scope and results of the checks that were actually performed.
Evidence column: **T** = automated test (file), **E** = browser E2E, **M** = manual/mutation check run once, **C** = code review only, **—** = not verified.

## 1. Assets and actors

| Asset | Why it matters |
|---|---|
| Tenant data (tasks, comments, attachments, members) | Confidentiality between organizations is the core promise. |
| Credentials, sessions, 2FA secrets | Account takeover. |
| Integration secrets (Discord webhook URLs, Google refresh tokens) | Posting as the organization / reading+writing a user’s calendar. |
| Audit log | Accountability. |
| Availability of the job queue | Reminders and notifications. |

Actors considered: an **anonymous visitor**; an **authenticated user of organization A** attacking organization B; a **member with a low role** attacking higher roles (privilege escalation);
an **organization administrator** (trusted within their organization only); **malicious content** (XSS via titles/comments/files); a **compromised application process** (the damage a bug or injection could do given its database role);
an **external party** abusing webhooks/OAuth (SSRF, forged callbacks). Out of scope: a malicious platform operator with database owner access, denial-of-service at network level, supply-chain compromise beyond dependency auditing.

## 2. Controls and evidence

### 2.1 Tenant isolation (two independent layers)

| Control | Evidence |
|---|---|
| Every tenant operation goes through `withTenant()`: it authenticates the *user id*, verifies an **approved** membership of the *requested* org (the id from the URL is only a request), loads that user’s role assignments, then sets the transaction-local database context. Non-members, pending, suspended and revoked users get **404** (existence is not disclosed). | T `tenant-isolation.test.ts`, `rbac.test.ts` · E `04-security` (cross-tenant URL/API/search probes) |
| **PostgreSQL row-level security**, `ENABLE` + `FORCE`, on every tenant table, keyed to `app.org_id`. Queries written *without* an org filter still return only the current org (tested by running unfiltered queries). | T `tenant-isolation.test.ts` · `pnpm verify:database` checks FORCE RLS on every table |
| Composite foreign keys `(org_id, id)` stop a row pointing at another tenant's row for the work-management tables (tasks, projects, labels, assignments, comments, …); CHECK constraints guard task invariants. Not covered by a composite key: `role_assignments.role_id` and `invitations.role_id` (a simple key to `roles`; another organization's custom roles are invisible to the caller through row-level security, so using one answers 404), and id columns that are only references (`notifications.task_id`, `audit_logs.target_id`, job payloads). | T `tenant-isolation.test.ts` (“database constraints”) |
| The runtime role is `NOSUPERUSER NOBYPASSRLS` and is not the owner of the tables (the owner has extra, policy-granted powers: creating organizations, editing system roles, purging old audit rows); in production-like tiers the app **refuses to serve (503)** if the connected role bypasses RLS or owns the tables. The check covers tenant and background-job transactions; the few self-service paths that do not use `withTenant` (account, calendar, series generation, privacy) do not call it, and a good verdict is cached for an hour. | T `ops.test.ts` · `pnpm verify:database` |
| Scope resolution (which department/team/project a task belongs to) always comes from the database, never from the request. | C · T `rbac.test.ts` |
| Foreign ids smuggled into your own org’s URLs (another tenant’s task id/project id) return 404 for read, write and status change. | E `04-security` (10 probes + 2 writes) |
| Notifications store identifiers only; text is rendered at read time after a **fresh access check**, so losing access removes the content. Search, saved views, dashboard, calendar and timeline apply the same permission filter. | T `notifications.test.ts`, `productivity.test.ts` |

### 2.2 Authorization (RBAC)

Scoped role assignments (`organization | department | team | project`), union of rights, **deny by default**, no explicit denies; see [RBAC.md](RBAC.md). Controls: no privilege escalation (you cannot grant a role holding permissions you lack),
last-administrator protection (advisory lock; an administrator cannot demote/suspend themselves into lock-out), per-record authorization in **bulk actions** with per-item results (partial failure is reported, never hidden), custom-role permissions validated against the catalog.
The UI hides controls the user cannot use, but **the server re-checks every action**; the browser tests drive the API directly as a viewer and are refused (E `02-task-lifecycle`, `07-recurring`). `superadmin` is only a flag and grants **nothing** inside any organization.
Evidence: T `rbac.test.ts`, `account.test.ts`, `tasks.test.ts` (42), `productivity.test.ts` (bulk), unit `evaluate.test.ts`/`permissions.test.ts`; M disabling RLS on `projects` failed 4 tests, making `can()` always true failed 19.

### 2.3 Authentication and sessions

* Email + password (min 12, max 128 characters), **email verification required before sign-in**, Google sign-in optional, TOTP two-factor with **backup codes** (single use; the sign-in page offers them) — T `auth.test.ts` (18), E `01-onboarding`, `04-security`.
* Self-registration is gated by **administrator approval**; invitations are one-time, expire in 7 days, are bound to the invited e-mail address, and are stored **hashed** — a stranger cannot redeem someone else’s link (E `04-security`/`01-onboarding`, T `account.test.ts`).
* Session cookies: `HttpOnly`, `SameSite=Lax`; in a production tier also `Secure` with the `__Secure-` prefix (T `auth-hardening.test.ts`); 7-day sessions refreshed daily; the user can list and revoke sessions and sign out other devices (E `04-security`). A password-reset link expires after 2 hours (set explicitly in `src/server/auth.ts`, as long as the wait before another reset e-mail may be requested; Better Auth's own default is 1 hour), is single-use, and signs out every session when used (C).
* **No account enumeration** on the paths probed live on 2026-10-17: wrong password vs unknown user return the identical `401 Invalid email or password`; password-reset returns the identical message for known and unknown addresses; the organization-code form answers identically for valid and invalid codes (E `01-onboarding`); sign-up for an existing e-mail returns a normal-looking success with a synthetic user. M.
* Brute-force limits (database-backed, work across serverless instances): sign-in 5/min, sign-up 10/h, reset request 5/h, TOTP and backup-code verification 5/min, verification e-mail 5/h (per client address); **per-account limits that do not depend on the client address** (20 failed sign-ins per 15 min per e-mail address — a correct sign-in gives its attempt back, so normal use never counts —, **every route that sends an e-mail is also limited per address**: password-reset e-mails 1 per 2 hours (the link lasts 2 hours too; using it frees the limit at once), verification e-mails 1 per 10 minutes, sign-up 3/h, invitations 1 per 15 minutes per address and organization, and at most 20 notification e-mails per hourly window to one person (a fixed window that starts at the first e-mail, so up to about 40 can leave around the boundary of two windows; the rest are deferred, not dropped; `src/jobs/handlers/email.ts`); 10 failed code guesses per pending two-factor sign-in, `src/server/auth-throttle.ts`). An address is counted whether or not it has an account, so the answer does not say which addresses exist; an allowance unit is given back when nothing reached the address (the request was refused, Better Auth answered with an error, or the provider failed to send), and using a reset link frees that address's reset allowance. One consequence I did not close: while the e-mail provider is failing, a second reset or verification request for an address that has an account is answered like the first, where one for an address without an account is refused, so an outage briefly reveals which addresses exist; application limits: join 5/h, invite 50/h, accept 10/h, upload 20/min, bulk 20/10 min, search 120/min, task create 120/min, comment 60/min, calendar connect 10/h. T `auth.test.ts`, E `06-hardening` (search → 429 `RATE_LIMITED` at the 121st call).
* **CSRF:** mutating API calls require an `Origin` header equal to the configured `APP_URL`; a foreign or missing origin gets 403 (E `04-security`, `pnpm smoke`). Combined with `SameSite=Lax` cookies.

### 2.4 Browser-side protections

* **Content-Security-Policy with a per-request nonce and `'strict-dynamic'`**, no `unsafe-inline`/`unsafe-eval` for scripts in production, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`. Inline *style attributes* are permitted (`style-src-attr`) because the UI uses them; style elements need the nonce.
  `'strict-dynamic'` deliberately lets already-trusted scripts create scripts; what the policy stops is injected **markup** (inline handlers, `javascript:` URLs) — the E2E test injects both and the browser blocks them and reports the violation. E `06-hardening` (headers, unique nonces, no violations on 11 page types, injected-markup test, framing test).
* `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera, microphone, geolocation, payment, usb off), `Cross-Origin-Opener-Policy: same-origin`, HSTS in production, `x-powered-by` removed. E `06-hardening`.
* **No HTML rendering of user text; Markdown only through a hand-written, tree-based renderer.** Titles are plain text. Comments and descriptions go through `src/lib/markdown.ts` → `src/ui/markdown.tsx`: the parser returns a typed tree (no HTML string exists at any point), React builds the elements, and there is no `dangerouslySetInnerHTML`. Raw HTML in the text (`<img onerror>`, `<script>`) is shown literally. Only these elements can appear: `p br strong em del code pre a ul ol li blockquote hr span`. Links must be `http(s)://`, without credentials, whitespace or control characters; they open in a new tab with `rel="noopener noreferrer nofollow ugc"` and a screen-reader hint; a link whose visible address differs from its destination is annotated with the real host. Images are never embedded (no remote requests → no tracking pixels; CSP `img-src 'self'` would refuse them anyway). Headings are drawn as bold paragraphs, so a comment cannot break the page outline. A work budget (300 000 steps, 20 000 characters, nesting ≤ 5) keeps hostile input fast (adversarial cases: ≈ 25 ms with the budget, 0.6–1 s without — the test fails if the budget is removed). Evidence: `tests/unit/markdown.test.ts` (69 tests incl. a 37-payload XSS corpus checked structurally: element names, attribute names, and every `href`), E `02-task-lifecycle` (formatting works, hostile markup is text, no dialog fires). Mentions are structured ids, not parsed from text.
* **The product's name is administrator-chosen text that travels into an e-mail header and into HTML**, so it is held to a narrow rule (`src/domain/app-name.ts`): 1 to 40 characters, letters, numbers, spaces and `. , & ' ( ) + : ! ? _ -`, starting with a letter or number; whitespace runs (line breaks included) become one space; quotes, angle brackets, `@`, `;`, backslash, control and zero-width characters, direction overrides and emoji are refused (HTTP 422), and the database has a length check as well. It is judged again where it is used: the sender display name is built by `formatFrom` as an always-quoted string from the configured address, ignoring any name that fails the rule (so it cannot add a recipient, another header or another address), every page and e-mail escapes it like any other text, and a value that no longer passes the rule (a row edited by hand) falls back to the default. Only people who manage settings can change it (the same permission as the other organization switches, same-origin check, audited with the old and new value). The name is shown on pages before sign-in, so it is public by design. T `app-name.test.ts` (unit and integration), E `12-app-name`. Not verified: how the real mail provider and mail clients render a non-Latin sender name (see ENVIRONMENT.md).
* Open redirect: the sign-in `next` parameter accepts only same-site relative paths, rejecting `//host` and backslashes (C; not covered by an automated test).

### 2.5 Files

Server-side upload (≤ 4 MB, ≤ 25 per task) or **direct upload to Blob** (≤ 25 MB; the browser sends the bytes to the store with a 10-minute token that is bound to one object name `orgs/<org>/tasks/<task>/<uuid>`, 25 MB, the generic type `application/octet-stream`, no overwrite and no completion callback; the server then reads the stored object back and applies the same checks, deleting it if it fails — nothing the browser reports is believed) with **content sniffing**: the type is decided from the bytes and must agree with the extension; SVG, HTML, scripts and archives are rejected; filenames are sanitized and never used for storage — keys are opaque server-generated paths.
Downloads go through an authenticated, permission-checked route and are sent as `attachment` with `nosniff` and a sandboxing CSP; the Blob store itself is private. T `attachments-http.test.ts`, unit `files.test.ts`, E `02-task-lifecycle` (png round-trip byte-for-byte; html refused).
**Not done:** malware scanning, previews/thumbnails (so no image-decoder attack surface), and **file contents are not covered by backups** (see [BACKUP_RESTORE.md](BACKUP_RESTORE.md)).

### 2.6 Secrets and integrations

* Discord webhook URLs are validated strictly (host allow-list, path shape, https, no userinfo/ports/redirects → **SSRF-resistant**), encrypted at rest with AES-256-GCM using AAD bound to the row, never returned by the API (only a hint like `…xyz`), never logged. Messages use `allowed_mentions: {parse: []}` (no `@everyone`), are generic unless the destination opts in to details, and the destination auto-disables on repeated or permanent failure. T `discord.test.ts`, unit `discord-url.test.ts`, `crypto.test.ts`.
* Google Calendar: OAuth with **PKCE and a hashed single-use `state`**, only the refresh token is stored (encrypted, AAD `cal:<id>`), event ids are deterministic (no duplicates on retry), sync is **one-way** (the client has no read function). T `calendar.test.ts` (29) against a **fake Google** — see §5.
* **Key rotation:** set the new key as `APP_ENCRYPTION_KEY`, the old as `APP_ENCRYPTION_KEY_PREVIOUS`, deploy, run `pnpm rotate:key` (re-encrypts every webhook and refresh token; reports any value no key can decrypt and never overwrites it), then drop the previous key. T `rotate-encryption.test.ts`.
* Logs are structured JSON with key-based redaction of passwords, tokens, cookies, secrets and webhook URLs (T `logger-env.test.ts`). Job errors store only an error *class*, never a response body. Audit metadata holds counts/ids, not content.

### 2.7 Database-level protections beyond RLS

* **Audit log is append-only for the application** and cannot be shortened below 90 days even by a compromised application ([RETENTION.md](RETENTION.md)). T `tenant-isolation.test.ts`, `retention.test.ts`, `owner-role.test.ts`; `pnpm verify:database`.
* The runtime role cannot create organizations or modify system roles, even when it sets the worker flag (it has no grant; the owner-only policies are bound to the migration role). T `owner-role.test.ts`.
* Task activity history is append-only for tenants; only the retention job, in worker context, can delete the history of tasks already in the trash. T `retention.test.ts`.

### 2.8 Availability and abuse

Durable Postgres job queue: leases, bounded retries with jittered back-off, dead-lettering, idempotent handlers keyed by dedupe keys, rolling-deploy safe (a worker claims only kinds it knows). Replay safety for outbox events, notifications, e-mail (idempotency key), Discord and calendar. Job health is visible in Settings and `/api/health/ready`. T `queue.test.ts` (16), `notifications.test.ts`, `reminders-digest.test.ts`. `GET /api/cron/tick` (and its quick pass `?fast=1`, which a server poller calls every second) accepts only `Authorization: Bearer $CRON_SECRET`, compared in constant time and never read from the query string (T `email-schedule.test.ts`); the poller therefore needs that one secret in its environment (a root-owned file the service user can read, README_VPS step 9b) and nothing else. It runs only the kinds of work people are waiting for, in a bounded time, and the same lease and de-duplication rules apply, so a poller cannot send anything twice.

## 4. Security review findings made during Phase 5 (all fixed and tested)

1. **Owner-bound RLS gap:** a plain database owner without `BYPASSRLS` could not run the bootstrap, sync system roles, or execute the audit-retention function, because `FORCE ROW LEVEL SECURITY` binds the owner too. Found by building a database owned by a plain role; fixed with owner-bound policies (migrations `0011`, `0012`) that do **not** widen the runtime role.
2. **`pg_dump` fails for such an owner** for the same reason (verified). `scripts/backup.sh` now checks the role first and explains.
3. **`/api/health/ready` could not read the migrations table** as the runtime role → readiness reported `down`; found by the E2E run, fixed by a read-only grant.
4. **Time zone:** the UI computed “today/overdue” in Asia/Bangkok instead of the user’s profile time zone; found by the E2E “My tasks” test, fixed.
5. **MFA recovery:** backup codes were generated but the sign-in page could not accept them; fixed and covered by E2E.
6. **Accessibility defects** found by axe: label-in-name on icon buttons, calendar grid roles, keyboard-unreachable scroll regions, off-screen menu in the tab order, absolutely-positioned screen-reader text widening mobile pages; all fixed.
7. **Row-level security was never enforced at runtime** (`checkRlsEnforceable` existed but nothing called it): now a guard in `withTenant`/worker contexts in production tiers.
8. **No security headers / CSP:** added (see §2.4). No request ids: added `x-request-id` (caller ids accepted only if they match `^[A-Za-z0-9-]{8,64}$`).

### Final test pass (route sweep, race tests, UI administration tests) — additional findings, all fixed

9. **HTTP 500 on a NUL character** in any text (`?q=%00`, a title containing `\u0000`): PostgreSQL cannot store it and the driver surfaced an internal error. Now rejected at every boundary with a 422 (`handle()`, `readJson`, and the Better Auth route). Found by the all-routes sweep.
10. **Attachment cap race:** simultaneous uploads from several users stored 28 files on a task capped at 25. The upload now locks the task row. Found by `concurrency.test.ts`.
11. **Bulk-update deadlock:** two bulk requests over the same tasks in opposite orders deadlocked (≈ 13 s) and reported items as `ERROR`. Rows are now locked in one global order and the version read is taken under the lock. Found by `concurrency.test.ts`.
12. **Calendar connect answered before the membership check** (a non-member could learn whether Google is configured). Order fixed; the sweep requires 404 for every route and method.
13. **Irreversible administrator actions had no confirmation** (revoke a member, delete a role / Discord destination / custom field): added.
14. **A refused custom-field value was thrown away** from the form instead of being kept for correction; fixed.
15. **Query parameters leaked into logs.** Drizzle's "Failed query" message embeds the bound parameters (task titles, e-mail addresses) and PostgreSQL's own messages quote the offending value (`invalid input syntax for type uuid: "…"`), so logging `error.message` would have put user content into the logs and, later, into an error tracker. Found by the error-reporting test. All error logging now goes through `describeError()` (`src/lib/error-report.ts`): database errors are reduced to the SQLSTATE code, its meaning and the constraint/table names; stack traces keep only `at …` lines; the query string and headers of the request are never recorded. Covered by `tests/unit/error-report.test.ts` and `tests/integration/error-reporting.test.ts` (real driver failure).
16. Verified rather than fixed: password reset **does** revoke all other sessions; sign-in `next` cannot redirect off-site (7 hostile forms tried); no permissive CORS headers or honoured preflights; suspension and role removal take effect on the very next request; mass assignment through sign-up / update-user / `PATCH /api/me` is ignored or refused.
17. **Account erasure and data export (new):** both need an authenticated session, are rate limited per user, run against the runtime role (RLS applies), and never include credentials. Erasure re-checks the password with Better Auth's own verifier (a wrong password is a 422, not a 401, so the browser keeps the session), demands the typed address, refuses platform administrators and sole administrators, and is one transaction. See [RETENTION.md](RETENTION.md#account-erasure). Tests: `tests/integration/privacy.test.ts` (9, including three deliberate breakages that were caught), `tests/e2e/09-session-security.spec.ts`.
18. **Whole-system security re-check (private-use scope), findings fixed:** (a) *Sign-in throttling trusted a client-controlled header.* Better Auth keys its limits on the address in `X-Forwarded-For`; against a production-tier build started locally, three different forged values each got a fresh allowance. Where the platform sets that header itself (believed to be the case on Vercel, **not verified here**) this does not matter; anywhere else it allowed unlimited password guesses. Fixed by the per-account limits above (tests `tests/integration/auth-throttle.test.ts`, 25, seven deliberate breakages caught; a first version that also counted correct sign-ins was caught by the browser tests, which sign in far more than 20 times, and was changed to count only failures). The trade-off is stated in the code: anyone who knows an address can use up its allowance and delay that person's sign-in until the 15-minute window ends. (b) *Organization bundles (`pnpm org`):* the checksum detects damage, not forgery, so a hand-built bundle with a recomputed checksum could carry rows for another organization. It was already refused late (the post-insert row count failed and the whole transaction rolled back, tested), but the check is now explicit, runs before anything is written, and names the table and row (`assertOwnRows`, 2 tests, mutation-checked). Bundles are operator-only files; keep them as private as a database dump.

19. **Independent review (four read-only reviewers; every finding below was checked by hand or by a test that failed before the change, and nothing a reviewer reported was applied unchecked):**
    * *Fixed.* (a) Sign-in with a form-encoded body was processed by Better Auth but never counted by the per-account limit (25 wrong guesses all answered 401): the two credential routes now accept JSON only (415 otherwise). (b) **Open redirect after sign-in:** `next=/<TAB>/evil.example` passed `safeNext` and, in Chromium, landed the user on the other site after a successful login (reproduced); replaced by `src/lib/safe-next.ts`, browser test extended. (c) **A bare `http://` or `https://` in a comment or description crashed the task drawer for everyone who opened it** (a null dereference in the Markdown autolink code; reproduced; 20 000-string fuzz added). (d) A JSON array of ≈125 000+ elements overflowed the stack in the NUL check and answered 500. (e) Better Auth's own `update-user` and `sign-up` accepted a display name of any length (100 000 characters tried) and control or bidi characters, bypassing the 100-character limit of `PATCH /api/me`; now bounded on both (names from Google are cleaned instead of refused). (f) **Pending invitations outlived the people they concerned:** a suspended administrator's unused invitation, or a suspended member's own older invitation, let someone back in; invitations sent by or addressed to a person are now voided when they are suspended, revoked or erased (a deliberate new invitation still brings someone back). (g) Swapping the primary and a co-assignee did not need `task.assign`, nor did a recurring series that assigns someone else. (h) Direct-upload object names accepted capital letters, which the cleanup sweep (lower-case prefix, case-sensitive store) could never find; one spelling only now. (i) Organization bundles: an unencrypted file was accepted even when a passphrase was set; new files use scrypt N = 2^17; a file that unpacks to more than 1 GiB is refused; a truncated sealed file gives the normal error; **export silently left out any table the exporting role could not read** (reproduced) and now fails loudly. (j) A production build with `APP_ENV=development|test|e2e` at a real address now refuses to start. (k) The RLS guard now also refuses a runtime role that owns the tables (the owner can create organizations; reproduced). (l) Denied requests are written to the audit log at most 30 per person per organization per 10 minutes. (m) **Links in e-mail, Discord and calendar events pointed to a page that does not exist** (`/o/<org>/tasks/<id>`; the page is `?task=<id>`). (n) Scripts: `db:migrate` did nothing, and exited 0, from a path containing a space; the attachment tools used a local folder without saying so when the Blob token was missing; `pnpm privacy` preferred the owner connection string. (o) Documentation: rotating `BETTER_AUTH_SECRET` also makes every stored two-factor secret and backup code unreadable (**verified by a test**; `pnpm auth:reset-2fa` added), the restore steps told the operator to put the owner connection string on Vercel, a Neon branch copies production data, and several claims were overstated (composite keys, "nobody can edit audit rows", where the RLS guard runs).
    * *Reported by a reviewer from reading the code; I did not reproduce them and changed nothing:* the time a request takes reveals whether an address has an account (password reset and sign-up wait for the e-mail provider only for existing accounts; the routes are limited per address, see the limits above); the lockout side effects of the per-account limits are stronger than item 18 says (anyone can also hold a known address's password reset: one per 2 hours); Google sign-in does not ask for the TOTP code (Google is then the second factor; by design of Better Auth); unfinished direct uploads count against no byte quota (token requests are limited to 20 per minute per user, objects are swept after the grace period) so a member could fill the Blob store; a holder of `project.update` can replace the set of teams on a project, including removing others; rate limits taken inside a request that then fails roll back with it (a failing bulk request does not add to its own limit); labels and custom-field definitions are visible to anyone with `org.read`; `verify:database`'s visibility probes pass trivially on empty tables (its FORCE-RLS checks are the meaningful part); the scripts that build test databases (`e2e-setup`, `load-test`) create a login role with the password `app` on whatever server `E2E_DB_ADMIN_URL`/`LOAD_DB_ADMIN_URL` names (default: the local one).

20. **Registration switch, single organization, deleting structure, typed confirmation (new surface; independently reviewed, every finding below was verified and fixed with a test that failed first or a mutation check).**
    * *Registration switch.* `organizations.registration_open` (default on). Changing it needs `org.manage_settings` (administrators only), is audited, and works through one narrow door: the runtime role has `UPDATE` on that **one column** of `organizations` (a column grant in `scripts/grants.sql`) and the row-level-security policy `org_update` limits the row to the caller's own organization. Tested as a plain, non-superuser owner with a separate runtime role: the switch can be changed, another organization's row cannot, no other column can, and the worker flag does not widen it (`owner-role.test.ts`; `pnpm verify:database` checks the grants on a real database and fails if they were not re-applied). **After migrating, re-run `scripts/grants.sql`** or the switch fails with “permission denied”.
    * *Where it is enforced.* In the user-creation hook (every way of getting an account, e-mail or Google) and in front of Better Auth's sign-up route (`guardSignUp`), and in `requestAccess`. Closed means: refused unless the address holds a valid, unused, unexpired invitation. In front of the route the guard also (1) requires a JSON body, because Better Auth reads form bodies too and those walked round the guard (found by the review; now 415), and (2) judges name and image before Better Auth looks the address up, because the hook only runs for addresses without an account and so told a caller which addresses were registered (also found by the review, and older than this change: now the same 400 for everyone). Tested by `registration.test.ts`, including a request that skips the guard, form and multipart bodies, expired/revoked/used invitations. **Not exercised:** the Google callback itself (only the shared hook was); a refusal there lands on our own sign-in page (`onAPIError.errorURL`, `errorCallbackURL`), which shows a Thai/English message and never prints the text it was given (e2e `11`).
    * *Information leak, accepted and rationed.* While closed, the sign-up answer reveals whether an address has a pending invitation. All sign-up attempts then share one allowance of 60 per hour and get 429 beyond it, whether or not the address is invited, so a caller cannot sweep addresses; the allowance is global because per-address limits behave badly behind a spoofable `X-Forwarded-For` (item 18). The cost: someone hammering the endpoint can make invited people wait for the next hour (someone who already has an account can still accept an invitation link). `/api/auth-config` is public and says whether registration is open and whether exactly one organization exists; nothing else about any organization.
    * *Request access without a code.* With exactly one organization, `POST /api/access-requests` may omit the code. With several organizations omitting it creates nothing and still answers “sent”; an unknown code still looks like success. A **closed** organization answers `REGISTRATION_CLOSED` (403), which reveals that the organization exists to someone who already knows its code (5 attempts per hour per user).
    * *Single organization.* `pnpm bootstrap` refuses a second organization unless `--allow-additional` is passed, refuses to invite anyone into the code of a **deleted** organization, and takes a database lock so that two bootstraps at the same moment (or a bootstrap racing the system-role sync, which now takes its own lock) cannot both succeed. This is an operator control, not a database constraint (see [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md)). `pnpm org import --replace` keeps the registration switch as it is now, so restoring an older bundle never re-opens a closed registration.
    * *Deleting departments, teams and projects.* New `DELETE` routes, each re-checking the permission on the server (`department.manage` organization-wide, `team.manage` for the team's department, `project.delete` for the project's scope) **before** it looks at the typed name or takes a row lock, 404 for ids of another organization, audited (`department.delete`, `team.delete`, `project.delete` with counts, plus one `role.unassign` entry per access that was removed). Everything that referenced the deleted thing is cleaned up in the same transaction (role assignments, project links, team-shared views, Discord destinations including their secret, recurring series, and for a project its tasks, which are announced as deleted so calendar entries go). **Races:** every writer that adds something under a department, team or project (create team/task/series/destination/view/assignment, link a team to a project, restore a task, generate a recurring occurrence) now takes a share lock on that live parent, so a deletion in progress waits for it (and takes what it created along) and a deletion that has committed makes it fail with 404; before this, a task could be created in a project at the moment it was deleted and stay visible to organization-wide readers (found by the review; `structure-delete.test.ts` holds two transactions open against each other for each case). Personal-data export treats work in a deleted project the same for everyone (left out, counted). Tested for who may and may not delete (including a department-scoped administrator against another department, a team-scoped administrator against their own team, and another organization's administrator), that neighbours are untouched, and that the deletion cannot be repeated (`structure-delete.test.ts`, browser spec `11`). **Every administrator can do this, and it cannot be undone from the interface.**
    * *Typed confirmation.* Deleting a department, team or project requires the exact name in the request body (`{"confirm": "<name>"}`, 422 `val.confirm_mismatch` otherwise, nothing changed), with one shared comparison for browser and server (`src/lib/confirm.ts`: Unicode NFC, spaces at the ends ignored, runs of spaces counted as one, case and look-alike characters **not** folded; `confirm.test.ts`). The browser uses the same dialog (`useTypedConfirm`) for custom roles, Discord destinations, custom-field archiving, recurring series, invitation cancelling, member revoking and attachment deleting, where only the permission is checked on the server. The review found that this dialog could not be typed into by a real person (focus was pulled to the close button after each keystroke; the e2e helpers re-focus the field and could not see it): fixed in `useDialogBehaviour` and covered by an e2e step that types with real keystrokes and asserts focus. Not typed, by choice: task deletion, comments, views, dependencies, role-assignment removal, suspension, calendar disconnect ([KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md)).
    * *Operations.* `/api/health/ready` treats a database **ahead** of the build as healthy-with-a-note (that is what an instant rollback looks like); only a database behind the build is down. The restore drill accepts a one-organization database and checks the column grant on the restored copy. Restoring an older dump or rolling the application back to a build older than 0014 re-opens registration (the old code does not know the switch): the runbooks now say to re-check Settings → General.

## 5. What has NOT been verified

* **Any real third-party service.** Resend, Google (OAuth, Calendar API), Discord, Vercel Blob, Vercel Cron and Neon were never contacted. Their behaviour is represented by fakes (`tests/integration/google-fake.ts`, injected `fetch`, a file e-mail sink, an in-memory/filesystem object store). Mock-based tests prove *our* handling of the documented request/response shapes, not that the live service accepts the requests. Use `docs/DEPLOYMENT.md` §8.
* **Neon specifics:** transaction-local `set_config` through the pooler, the default owner’s attributes (`BYPASSRLS`), plan limits, point-in-time restore.
* **Penetration test / independent review:** none. The all-routes sweep sends > 500 malformed requests and cross-tenant probes with real ids, but it is a scripted regression test, not an adversarial human assessment, and there was no load or denial-of-service testing and no DAST scanner run.
* **What row-level security does and does not protect:** it stops *application bugs* (a forgotten `WHERE org_id`) from leaking data. It does **not** stop an attacker who can already execute arbitrary SQL as the runtime role, because that role can set the same session variables the application sets (`app.org_id`, `app.worker`). Preventing SQL injection is therefore the first line (all queries are parameterized through Drizzle; the only `sql.raw` calls are three in `src/data/dashboard.ts`, which interpolate compile-time constants (the status and priority enum values and a loop index), never request data; there is no other string-built SQL — checked by search), and database credentials must be protected like the data itself.
* **Live probe of a production-tier build (this re-check):** started with `NODE_ENV=production`, an https `APP_URL` and the least-privilege role, two organizations with one administrator each. Observed: the session cookie is `__Secure-better-auth.session_token; HttpOnly; Secure; SameSite=Lax`; every request by the first administrator to the second organization's tasks, comments, activity, projects, members, audit log, search, change signals, roles, integrations and calendar answered the same 404 as a random or malformed organization id; writes against the second organization's task (edit, status, comment, delete, create in its project, label, upload token, invite, approve) all answered 404 with a valid same-origin header and left the data unchanged; writes with a foreign, `null` or missing `Origin` answered 403; no or garbage cookie answered 401; the cron endpoint refused a wrong bearer; started with a superuser database role the tenant routes answered 503 and the log said why. This was done by hand with `curl` against **local** PostgreSQL, not Neon, and is a point-in-time check, not a regression suite (the regression suites are the integration and browser tests).
* **Independent review:** four reviewers read the code (authentication and sessions; tenant isolation and authorization; files, content, secrets and jobs; operator tooling, configuration and documentation) and their findings are in §4 item 19. They were other instances of the same model working read-only, not human security professionals, and none of them could run the application against the real services. That is better than the author alone and much less than a professional penetration test.
* **Vercel's handling of `X-Forwarded-For`** (whether a client-supplied value is overwritten) and of the per-address limits behind it.
* **Browser coverage:** Chromium only (desktop and a 375 px viewport); Firefox/Safari not run. Screen readers were not used; axe covers the rules it can detect automatically (≈ 30–40 % of WCAG issues), so manual testing is still required.
* Password-hash parameters and token entropy are Better Auth defaults (C); invitation/state tokens are 256-bit random values (C).
* Malware scanning of uploads; e-mail bounce/complaint handling; WAF; per-IP rate limiting at the edge (limits here are per user/key in the database; Vercel/Cloudflare firewall rules are recommended in front).

## 6. Incident procedures

| Situation | Do this |
|---|---|
| **A user’s account is compromised** | Suspend their membership (Members → Suspend: takes effect on the next request, because membership is checked on every call), ask them to reset the password, then *Sign out other devices*. Review `Audit log` filtered to their actions. |
| **An integration secret leaked** (Discord URL) | Rotate the destination (Settings → Discord → Rotate) after revoking the webhook in Discord. Calendar: disconnect and revoke the app in the user’s Google account. |
| **`APP_ENCRYPTION_KEY` or `BETTER_AUTH_SECRET` leaked** | Rotate the encryption key with `pnpm rotate:key`; rotate `BETTER_AUTH_SECRET` (signs everyone out **and breaks every two-factor enrolment**: follow it with `pnpm auth:reset-2fa --all --yes` and tell people to enrol again — see ENVIRONMENT.md). Rotate the integration secrets themselves too if the database was also exposed. |
| **Database credentials leaked** | Change the Neon role passwords, update Vercel variables, redeploy; review recent audit entries; run `pnpm verify:database`. |
| **Suspected cross-tenant exposure** | Take the app offline (remove the production domain or rotate `DATABASE_URL` to an invalid value → 503), preserve logs (`x-request-id` correlates a user report with server logs), reproduce with a test in `tests/integration/tenant-isolation.test.ts`, fix, run the full suite and `pnpm smoke`, then restore service. |
| **Everyone locked out** | Use the operator bootstrap (`pnpm bootstrap …` issues a fresh administrator invitation for an existing organization). |
| **Job queue stuck/dead** | Settings → Job health, `/api/health/ready`; dead jobs are kept 30 days. Re-run the tick; fix the cause (usually a revoked credential). |

**Reporting:** no security contact address is configured in this repository. Decide one (for example `security@<your domain>`) and publish it before launch.
